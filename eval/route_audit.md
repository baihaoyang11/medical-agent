### 5.1 带上重排再看一遍

线上 `RERANK_STRATEGY` 默认是 `keyword`（重排是开的），所以只比不带重排的版本会低估所有方案。
下表把同一套映射换成「检索器 + 重排」重新算：

| 配置 | R@5（含重排） |
|---|---|
| 统一 `dense+rerank` | 0.974 |
| 统一 `hybrid+rerank` | 0.914 |
| **完美路由 + 重排** | **0.983** |
| **真实路由 + 重排** | **0.931** |

**基线取统一 `hybrid`（0.905）**，理由：路由层只决定 dense / sparse / hybrid，
重排是其后独立的一步。拿 `hybrid+rerank` 当基线会把两件事的收益混在一起算。

**读法**：
- 完美路由的上限收益：+0.086
- 真实分类器拿到：+0.009
- 收益留存率：**10%** —— 路由设计赚到的提升，有 90% 被分类错误吃掉了

- **决定性对比（同为线上口径，均含重排）**：真实路由 + 重排 0.931 **低于**统一 `dense+rerank` 的 0.974。
  换句话说，把全局默认改成 `dense`（`RETRIEVER_DEFAULT=dense`，改一行配置）比上线整套检索器路由还强 +0.043。
  **一个方案如果打不过它自己的简化版，就不该上线** —— 这是比"证据不显著"更硬的否决理由。

## 7. 结论

1. **检索器路由的前提是分类器可用**。当前 58% 的兜底率意味着映射表再精细，也只会影响不到一半的请求。
2. **先修分类器，再谈选检索器**。顺序搞反了，就是在一个失效的分支上做优化。
3. 分类器该怎么修：关键词表只覆盖了"用户说了什么词"，没覆盖"用户想要什么"。
   可行的方向是 query embedding 与类型原型的相似度（零样本、无需标注），
   或者直接上小模型分类。两者都需要先有一批带标注的 query —— 现在的 116 条够起步，不够定论。
4. 这个审计之所以值得单独做：如果不测路由器，就会以为"加了检索器路由 = 性能提升"，
   而实际上 90% 的请求连门都没进。**测中间环节，比测最终指标更能定位问题。**
5. **最该注意的一条**：真实路由 + 重排拿到 0.931，而把默认值改成 `dense` 就是 0.974（差 +0.043）。
   前者要维护分类器 + 映射表 + 开关 + 一堆边界测试，后者是环境变量里改一个词。
   **收益更小而成本更高，就是不该做** —— 这是 `RETRIEVER_ROUTING` 保持默认关闭的最终理由，比"证据不显著"具体得多。
6. 但 `dense` 这条路也有前提：它在**单库**评测里赢，生产是 QA + PDF 双库，教材段落长、术语密集，BM25 的贡献可能不同。改默认值之前应该在双库上补一次对照，而不是直接拿这个数字上线。
