# 离线检索评测

## 为什么需要这个

没有评测的"优化"无法证伪。改一个 chunk 大小、换一个 `rrf_k`、加一层重排，
都会让人觉得"好像更准了"——这种感觉通常来自最近看过的几个 case，不是数据。

这个目录做的事：**给定一套固定的语料和金标，用固定指标横向比四种检索配置**。
它的输出是一个表格，不是一个感觉。

## 怎么跑

```bash
python tasks.py eval          # 真实语义向量（bge-small-zh，首次会下载约 95MB）
python tasks.py eval-fast     # 零依赖确定性向量，CI 用，约 1 秒
```

结果写到 `eval/report.md` 和 `eval/results.json`。

## 语料长什么样

| 组成 | 数量 | 作用 |
|---|---|---|
| 核心知识点 | 48 | 8 个主题 × 6 个侧面，每个 120~170 字 |
| 无关干扰 | 68 | 其他科室（眼科/口腔/皮肤/骨科等）的常识，与核心主题不重叠 |
| **合计** | **116 个 chunk** | |

**为什么是合成的，不是真实教材**：真实医学教材受著作权保护，逐页抽取的正文
等价于全文复制，不能随公开仓库分发（见根目录 README「已知边界」第 7 条）。
合成语料保证了这个仓库 clone 下来就能复现，代价是它测的是**检索器在受控难度下的
相对表现**，不是真实业务效果。换成真实语料后绝对分数会变，方法是同一套。

### 难度是怎么设计的

同一主题下的六个侧面（定义 / 饮食 / 用药 / 运动 / 并发症 / 监测）**互为难负样本**。
它们都讲"糖尿病"，但回答的是不同问题。检索器必须区分到"侧面"这一层，
而不是停在"主题"这一层——这是真实场景里最常见的错法：用户问饮食，
系统返回三段讲用药的，因为它们都含"糖尿病"，向量相似度都很高。

## 100 条 query 的构成

- **96 条**来自 48 个知识点 × 2 种问法
  - `formal`：书面表述（"糖尿病患者如何进行运动治疗"）
  - `colloquial`：口语表述（"血糖高的人跑步有用吗"）
- **4 条**急症（胸痛、昏迷、服药过量、呼吸困难），**没有金标**，不参与 recall

这个"两种问法"的设计是整个评测的核心：

> 书面问法与正文共享大量词汇，BM25 能吃到；口语问法几乎不共享词，只能靠语义。
> 如果混合检索真的有意义，它应该**同时不输给两边**，而不是"平均分高一点"。

急症 query 的存在是为了保证 query 分布贴近真实，同时提醒：**这类问题不该走检索**，
路由层直接短路更安全，也不列入召回考核。

## 四种配置

| 配置 | 说明 |
|---|---|
| `dense` | 纯向量检索 |
| `sparse` | 纯 BM25（字符二元组，k1=1.5, b=0.75） |
| `hybrid` | 两路各召回 3k，**调用 `core.rrf.rrf_merge`** 融合 |
| `hybrid+rerank` | 混合召回 3k 后，**调用 `core.rerank.KeywordReranker`** 重排 |
| `oracle` | 上限参考：把金标强行提到第一位，用于判断瓶颈在召回还是排序 |

**关键设计：`hybrid` 和 `hybrid+rerank` 直接 import 生产代码，不是复刻一份。**
评测里自己实现一套融合逻辑是最常见的自欺——那样测的是评测脚本，不是系统。

`oracle` 那一行回答一个具体问题：**重排最多还能捞回多少**。
如果 `hybrid` 和 `oracle` 差距很小，说明瓶颈在召回，换更强的重排器没有意义；
差距大，才值得投入。

## 指标

| 指标 | 含义 | 为什么需要 |
|---|---|---|
| `recall@k` | 金标是否进前 k | 和"上下文里有没有答案"直接对应 |
| `MRR` | 第一个正确结果的倒数排名 | recall 看不出排第 1 还是第 5 |
| `nDCG@5` | 对位置打折的排序质量 | 排第 5 的正确文档对生成的价值低于排第 1 |

三个一起看，是因为**只看 recall 容易自欺**：把 20 条全召回，recall=1.0，
但正确那条排第 19，上下文预算早就把它截掉了。

## 已知局限

1. **单库，不覆盖双路路由**。生产系统是 QA 库 + PDF 库双路检索，按问题类型分配
   `qa_k` / `pdf_k`。这里的语料只有单库，所以「路由分流带来的收益」无法在此评测，
   只能验证「融合与重排」这一段。
2. **合成的难负样本不如真实分布狡猾**。真实场景里会有大量"看起来相关但版本过期"
   的文档，这里没有建模。
3. **没有测答案质量**。这里只测检索。端到端的答案忠实度需要另一套金标
   （query → 答案要点），那是下一个阶段的事。

## 复现性

- 语料由 `knowledge.py` + `filler.py` 硬编码，无随机种子依赖
- `hashing` embedder 用 `zlib.crc32` 而不是内置 `hash()`——后者对字符串带随机盐，
  同一条文本换进程就变，评测会静默不可复现
- `results.json` 记录 embedder、维度、耗时、语料规模，便于比对不同环境的运行结果
